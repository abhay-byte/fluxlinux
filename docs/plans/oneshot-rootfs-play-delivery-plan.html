## 3. Implementation plan (surgical, in order)

### Step 0 — Pin & print existing bytes + BINDING packaging-source rule (STOP gate)

For each of the 7 in-scope distros (debian, alpine, ubuntu, kali, archlinux→`distro_arch`, manjaro, chimera), print `distro | filename | expected SHA-256 | bytes` and run `sha256sum` against the local pinned archive. Source values come from `DistroInstallProfile` constants (R4). Record the 7-line table in the worker report.

**Binding packaging-source rule (fixes review CRITICAL-3; clean tree has no `assets/rootfs/**` — gitignored per R9):**
- **Rule A (preferred, try first):** if a local `assets/rootfs/<file>` (or the `rootfs`-tag release bytes already on disk) is present AND `sha256sum` matches the `DistroInstallProfile` pin, stage THOSE bytes verbatim into the `:distro_*` feature assets.
- **Rule B (allowed fallback ONLY for build-time staging, NOT a runtime fallback):** if Rule A bytes are absent on this checkout, the worker MAY fetch the **exact** `DistroInstallProfile.rootfsUrl` bytes for that distro SOLELY to stage them into `distro_*/src/zenithblue/assets/payloads/distro_*/<file>` at build time, then MUST `sha256sum`-gate them against the pin before packaging. This is packaging staging, not a zenithblue runtime HTTP path — the runtime ban in Step 2.4 is unaffected and absolute.
- **STOP condition (unchanged):** any missing file or SHA mismatch AFTER Rule A/B → STOP, do not package a substitute/rebuilt/different rootfs; report the exact distro. Do not invent URLs/checksums — only the SSOT `rootfsUrl` pin (R4). Record which rule (A or B) supplied each of the 7 archives in the report.
